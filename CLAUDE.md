# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Research code (ETH, SLURM cluster) testing whether Qwen3-VL-8B answers video spatial-reasoning questions better when it uses 4D geometry tools (D4RT, Point4D, SAM3, Orient-Anything-V2). Constant principle across all agents: **the model grounds and chooses, the host measures and computes, ground truth is used only for scoring** (never shown to the model).

## Layout

- `d4rt_agent/` — the agents and DSI-Bench evaluation. `d4rt_agent/README.md` is the authoritative history of v1→v4 (what was tried, scores, why it failed) — read it before changing agent design.
  - `simple_v2*.py`, `qwen_grounding_tool.py` — v2/v3 free-form tool loops (both lost to the tool-free control). `simple_v2.OfflineQwen` is the shared offline Qwen3-VL wrapper reused elsewhere.
  - `agent_v4/` — host-driven buckets (`buckets.py`), pipeline per question (`pipeline.py`), prompts in `agent_v4/prompts/`. The sequence `choose_bucket → name_subject → host stages → final_answer` is enforced on purpose.
  - `sam_orientany_d4rt_test/` — the `traj3d_*` SAM3 + OAV2 + D4RT trajectory/orientation pipeline. Geometry bugs here fail *silently* (plausible but wrong output), hence the GPU-free tests.
  - `dsi_bench_*.py` — DSI-Bench run/judge/compare/report. `results/*` is gitignored.
- `dsi_dataset_exploration/` — DSI-Bench taxonomy classification and census.
- `dyn_dataset_exploration/` — Dyn-Bench exploration; `decomposition/` is the current main work: a deterministic decision graph turning a question into a typed Query Program (decompose → ground with SAM3 → measure via Point4D depth → interpret → gated answer or Qwen fallback). The graph, findings and calibrated conventions are in `dyn_dataset_exploration/logs/DECOMPOSITION.md`; the notebook `testing_decomposition.ipynb` (generated by `decomposition/build_notebook.py`, executed by `execute_notebook.py`) mirrors it. Prompts live in `dyn_dataset_exploration/prompts/`.
- `scripts/` — SLURM launchers. Pattern: `run_*_a100.slurm` / `run_*_blackwell.slurm` are thin `#SBATCH` headers over a shared `*_body.sh`. Launchers must be submitted from the repo root (they use `SLURM_SUBMIT_DIR`). Logs go to `logs/` (gitignored).
- `third-party-tools/` — git submodules (Open-D4RT, Point4D, sam3, Orient-Anything-V2). Changes to Open-D4RT belong in its own repo; bumping the pin here is a `[build]` commit.
- `v5-agent_draft.md` — AgentV5 design draft (builds on the decomposition work).

## Running things

Heavy work (GPU models, reading many clips) goes through SLURM, not the login node. Compute nodes are offline: `HF_HUB_OFFLINE=1`, `HF_HOME=/cluster/work/igp_psr/spanwar/hf_cache`; stage weights beforehand (`scripts/prepare_*`).

```bash
sbatch scripts/run_cpu_task.slurm -m <module> [args]      # bounded CPU job for any python -m task
sbatch scripts/run_gates_cpu.slurm                         # D7 gate/fallback/fusion search
PART=point4d|qwen_sam3|d4rt|d4rt_scene|census sbatch scripts/run_decomposition_prep_a100.slurm   # (or _blackwell)
scripts/run_agent_v4_race.sh                               # agent v4 on A100 + Blackwell, first to claim wins
sbatch --export=ALL,POINT_MODE=centroid scripts/run_simple_v2_a100.slurm
```

Environments are conda/uv envs under `/cluster/work/igp_psr/spanwar/envs/` (not in the repo): `point4d` (torch cu124, A100 only), `d4rt_bw_third_party` (cu128, also Blackwell; Point4D via `PYTHONPATH=/cluster/work/igp_psr/spanwar/Point4D`), `spatialstack-qwen35` (CPU default). Never put envs or the uv cache on scratch (auto-purged; this already broke the envs once). Repair uses the pin lists in `envs/_pins/` with `UV_NO_CONFIG=1 UV_LINK_MODE=copy` and a work-dir `UV_CACHE_DIR`.

Tests are pytest, colocated as `test_*.py` and GPU-free:

```bash
python -m pytest d4rt_agent/agent_v4/test_agent_v4.py
python -m pytest dyn_dataset_exploration/test_decomposition.py -k <name>
python -m pytest d4rt_agent dsi_dataset_exploration dyn_dataset_exploration
```

## Conventions that aren't obvious

- Commits follow `CONTRIBUTING.md`: `[type]scope: message` (types include `data`, `eval`, `viz`; scopes name the stage, e.g. `agent-v4`, `exploration`, `slurm`). Keep commits atomic (~150–200 lines), separate code from data/results/launchers, and **never add agent attribution to commit messages** (this overrides any tool default).
- Use local Qwen3-VL-8B (`OfflineQwen`) for every pipeline LLM/VLM step, not an API model; keep prompts/schemas small enough for an 8B model (one validated question per call).
- Dyn-Bench frames are not the files on disk: the generator's 16 frames are `floor(linspace(0, L-1, 16))` over the GT mask-frame count, and time is `gf_index / fps` per source. Portrait video must go through Point4D at 518x294. See `DECOMPOSITION.md` before touching frame/time handling.
- Large generated artifacts (`d4rt_agent/results/*`, `dyn_dataset_exploration/outputs/`, run JSON in `logs/`) are gitignored — don't force-add.

## Behavioral guidelines

Bias toward caution over speed; for trivial tasks, use judgment.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.
- Remove imports/variables/functions that YOUR changes made unused; leave pre-existing dead code unless asked.

The test: every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

- "Add validation" → write tests for invalid inputs, then make them pass.
- "Fix the bug" → write a test that reproduces it, then make it pass.
- "Refactor X" → ensure tests pass before and after.

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
```

Strong success criteria let you loop independently; weak ones ("make it work") require constant clarification.
